## Scope and actors

Problem/outcome: doc 01 — segment-2 SME leader gets an explained, trustworthy on-target verdict without hiring anyone. Release/phase: doc 02 MVP row.
In scope: manual/CSV-uploaded pipeline and P&L data; deterministic calc engine for month/quarter/year target-vs-actual; explained "why" reasoning; stale-deal detection; the invoiced/order-book/weighted-pipeline three-tier annual trajectory; a short onboarding step capturing four explicit Commercial Baseline benchmarks (sales-cycle length, revenue target, margin target + minimum acceptable margin, stale-opportunity threshold), editable afterward via a Company Settings page; single pilot user per business, basic login, no billing.
Out of scope: live Xero OAuth (doc 02 — V1); multi-tenant roles/permissions beyond per-business data isolation; billing/payments; segment 3 (win-driver attribution, capacity matching — doc 02 V2); marketing/procurement modules; public self-serve signup; onboarding fields with no corresponding calc rule yet — business type/B2B-B2C, seasonality, new-vs-existing mix, win-rate expectation, average deal value (V1); subjective data-confidence self-report — the objective confidence bands in RULE-009 already cover this more reliably; quote-validity/"at risk" as a signal distinct from stale-deal detection (V1 — a second staleness signal stacked onto an untested first one).

## Business rules and data constraints

| Rule ID | Rule/invariant | Applies to | Enforcement point | Failure outcome | Test |
|---|---|---|---|---|---|
| RULE-001 | **Commercial benchmarks** (sales-cycle days, revenue target, margin target + minimum acceptable margin, stale-opportunity-threshold days) are captured explicitly during onboarding (REQ-013) and are never silently overwritten by observed data — a benchmark stays exactly what the business set until the business changes it. Where a calculation requires a numeric threshold and no benchmark has been configured: for **sales-cycle and stale-opportunity-threshold**, the engine uses a clearly labelled platform default (sales-cycle: **30 days**; stale-opportunity-threshold default value still needs Dan's number — see open questions). For **revenue and margin targets, there is no sensible default** — an unconfigured target shows an explicit "no target set" state, never a fabricated figure; guessing someone's revenue target is a different kind of wrong than guessing a typical sales-cycle length. **Decided, 2026-09-19, corrected from an earlier draft that wrongly implied historical data could substitute for a benchmark — it never does.** | Commercial baseline | Calc engine | A degrading benchmark (e.g. cycle drifting from 30 to 60 days) must keep being flagged against the *original* 30-day benchmark, not silently re-baselined to 60 | AC-013-01 |
| RULE-009 | **Historical observation** (e.g. actual average sales-cycle, per-stage dwell time, computed from closed deals) is a separate, permanently-displayed figure alongside its related benchmark — never averaged into it, never used to redefine it. Each historical figure carries a confidence indicator based on qualifying record volume: 0 → no historical figure shown; 1–4 → "early indication"; 5–19 → "developing baseline"; 20+ → "established baseline." **These exact thresholds are illustrative, not fixed — tune once real data exists.** | Historical performance figures | Calc engine | Never let observed performance quietly become the new normal — that is precisely the drift RULE-001 exists to prevent | AC-006-01, AC-013-02 |
| RULE-010 | **Stale-opportunity threshold** is organisation-controlled, not a universal number — "stale" is industry-contextual (a PT's inactivity window might be 7–14 days, B2B 3–6 months, pharma 2+ years), so no fixed platform default is appropriate the way 30 days is for sales-cycle. Deterministic fallback chain: (1) the explicit threshold set during onboarding/Company Settings; (2) if unset, **50% of the organisation's sales-cycle benchmark, rounded to the nearest whole day**; (3) if neither the stale threshold nor the sales-cycle benchmark has been configured, derive from the 30-day MVP sales-cycle default → **15 days**. The historical observed sales cycle (RULE-009) never automatically alters this threshold. **Decided, 2026-09-19, from Dan's correction — a flat universal default would have been wrong.** | Commercial baseline | Calc engine | Never invent a single "one size fits all" stale window across industries | AC-010-02 |
| RULE-011 | A change to any commercial benchmark (sales-cycle, targets, stale threshold) takes effect for current/future calculations only — it must never retroactively alter a previously computed or displayed verdict. At MVP this is trivially satisfied, since verdicts are computed live each time and nothing is archived yet; it becomes load-bearing the instant any historical verdict snapshot or reporting-over-time feature exists (V1+), and must be honoured then without redesign. **Recorded now, while it's cheap, per Dan's own principle: historical behaviour informs the verdict, it must never silently redefine the organisation's commercial rules.** | Commercial baseline, future verdict history | Calc engine (current); reporting layer (future) | A settings change must not make last month's reporting "mysteriously change" | — |
| RULE-012 | **Rejected and replaced, 2026-09-19.** The original RULE-012 let a per-stage historical average (once confident enough) override the organisation's stale threshold for flagging — this was wrong, not just under-specified. Confidence bands govern *how a historical figure is presented*, never *whether it replaces the benchmark*. Corrected rule: **stale-deal flagging always uses the organisation's configured stale-opportunity threshold (RULE-010) — full stop, no exceptions, no confidence-based override.** The per-stage historical average is always shown alongside a flagged deal as separate, confidence-graded context (RULE-009), producing the actual commercial insight — e.g. "your threshold is 30 days; historically this stage averages 52 days" — which is a stronger signal than silently moving the goalposts to 52. Because onboarding (AC-013-01) requires the stale threshold before any verdict is reachable, RULE-010's fallback chain should rarely fire in normal MVP use — it exists as defensive architecture, not expected behaviour. | Pipeline deals, historical observation | Calc engine | Never let observed behaviour quietly redefine what "stale" means — that is precisely the drift RULE-001/009 exist to prevent, applied consistently to stale-flagging rather than treated as an exception | AC-006-03 |
| RULE-002 | If only an annual target is supplied, monthly/quarterly targets are derived by even distribution unless the user overrides them | Target figures | Calc engine | Verdict must visibly state when a target is derived vs. user-supplied, since even distribution is an assumption, not a fact — real businesses are seasonal | AC-003-02 |
| RULE-003 | Weighted pipeline is not a percentage-of-value calculation. A deal is either won or lost — there is no such thing as 50% of a deal's value. Instead, each open deal carries a qualification tier — **Too early / Unlikely / Likely / Highly likely** — reflecting how much evidence-based sales-methodology qualification (SPIN/MEDDIC/STAR-style questioning through to negotiation and objection handling) has actually been completed on it. Only deals tagged **Likely or Highly likely** feed the trajectory projection, and they contribute at **full deal value**, not a discounted one. **MVP: the owner self-tags each deal's tier directly in the upload template — their own judgment, not a scored one. A methodology-question checklist that derives the tier automatically from answered evidence is the headline V1/V2 differentiator (doc 02), deliberately not built at MVP.** | Open pipeline deals | Calc engine | Must be visible in the explainer (REQ-005) — which tier a deal sits in, and why, not just the resulting total | AC-012-01 |
| RULE-004 | Order book = sum of deals marked "won" with no corresponding invoice yet in the P&L data | Won deals | Calc engine | A won deal with no matching invoice row must not silently disappear from either pipeline or order book | AC-012-01 |
| RULE-005 | All monetary figures in GBP; display rounded to nearest £1, underlying calculation kept precise | All monetary values | Calc engine / display layer | Rounding must not compound into a materially wrong verdict at year view | — |
| RULE-006 | Each pilot business's data is stored in isolation — no shared query path across businesses, even though MVP has no formal multi-tenant auth | Data storage | Storage layer | A leak here is a security failure regardless of MVP status — per the app dev framework's own non-negotiable, this is never deprioritised for speed | — |
| RULE-007 | If the most recent upload is older than a stated threshold, the verdict must visibly flag itself as stale rather than present outdated data as current | Dataset freshness | Display layer | Silent staleness directly undermines the trust requirement in REQ-005 | AC-009-02 |
| RULE-008 | Pipeline coverage (the "2.1x of remaining target" figure) is reported as two distinct numbers, not one: raw open-pipeline value, and qualified coverage (Likely + Highly likely only). Never collapse them into a single figure. | Pipeline coverage calculation | Calc engine | This is the doc 01 co-packer symptom made visible: a pipeline that looks full on the raw number and is thin on the qualified one is precisely "full pipeline, behind target" — hiding the gap between the two would defeat the point of the tool | AC-006-02 |

Source of truth for all calculated values (target-vs-actual, coverage ratio, stale flags, trajectory segments) is the calc engine, computed fresh from the two uploaded files — never cached or hand-edited.
